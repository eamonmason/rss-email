### Where "(article X)" comes from

This is **Claude's own generated prose leaking a citation convention that was only ever scoped to the structured `top_articles`/`top_stories` fields**, not a rendering placeholder inserted by the code. There is no string anywhere in the codebase (`grep -rn "article [0-9]\|(article\b"` across `src/` and `tests/` turns up nothing) that programmatically emits `"(article N)"` — so the text is being typed by Claude directly into `tldr` / `relevance_to_reader` / `week_verdict` / cross-cutting `implication` / `personal.summary`, and the renderer forwards it verbatim.

### 1. The prompt and its citation instruction

File: `src/rss_email/brief_generator.py`

- `PROMPT_TEMPLATE` (lines 53–104) shows each article to Claude as `"(ID) [Source] Title"` (built in `build_prompt`, line 302: `lines.append(f"- ({item['id']}) [{source}] {item['title']}")`).

  ```
  Each article below is listed as "(ID) [Source] Title", e.g. "(12) [Hacker News] Title".
  In top_articles and top_stories, cite articles ONLY by their numeric ID in parentheses
  (e.g. "12") - never the title or source text, and never include the brackets or

  ```
  This instruction only constrains the `top_articles` / `top_stories` **array fields** in the JSON schema (schema shown at lines 66–84, e.g. line 74: `"top_articles": ["&lt;id1&gt;", "&lt;id2&gt;", "&lt;id3&gt;"]`). This is a direct consequence of the a5c7dcc fix (`git show a5c7dcc`): before that commit, Claude echoed exact titles for `top_articles` and the renderer looked them up by title (`match_title_to_url`); the fix moved to numeric-id citation (`ensure_article_ids`, `build_article_index`) specifically to stop malformed titles/brackets reaching the email. ### 4. Root cause verdict

It is **Claude embedding the citation directly in the prose string** — not a rendering-code placeholder that failed to get linked. The prompt (lines 95–98) only forbids everything *except* the numeric id in the `top_articles`/`top_stories` arrays; it never tells Claude to keep numeric ids **out of** `tldr`/`relevance_to_reader`/`week_verdict`/`implication`/`summary`. The render path (`_render_theme` et al.) has zero handling for citations appearing in those fields — it just `html.escape()`s and prints them.

Two complementary fixes are possible, and both are needed for robustness:
- **Prompt-side**: add an explicit rule like "Never mention an article's numeric id inside tldr, relevance_to_reader, week_verdict, implication, or summary — those are prose only; ids belong exclusively in top_articles/top_stories."
- **Render-side defensive strip/link**: since a5c7dcc's own reasoning was "never trust Claude's raw string, the renderer composes the display text" — the same principle should probably apply here: a regex sweep (e.g. `\(\s*(?:article\s*)?\d+\s*\)`) over `tldr`/`relevance_to_reader`/etc. before/after `html.escape`, either stripped or resolved via `article_index` into a real link, so a future prompt regression can't reintroduce the bug.

### A2. Render-side defensive helper (new function in `brief_generator.py`, placed right after `_render_article_links`, before `_render_theme` at line 569)

Design rationale: a bare `(article N)`-style citation is unambiguous — the word "article" makes intent clear — so it's safe to always resolve-or-strip it. A **bare** `(N)` is ambiguous (could be a legitimate parenthetical quantity/year/footnote in prose), so it's only touched when `N` actually resolves to a known article id; if it doesn't resolve, it's left untouched rather than risk deleting real prose. This mirrors the a5c7dcc philosophy (only ever assert what we can *prove* resolves) while bounding false-positive risk on the ambiguous pattern.

```python
_ARTICLE_CITATION_RE = re.compile(
    r"\(\s*articles?\s*#?\s*(?P&lt;ids&gt;\d+(?:\s*(?:,|and|&amp;)\s*#?\d+)*)\s*\)"
    r"|\(\s*(?P&lt;bare_id&gt;\d{1,4})\s*\)",
    re.IGNORECASE,
)
_CITATION_ID_RE = re.compile(r"\d+")


def _linkify_or_strip_citations(text: str, article_index: Dict[str, Dict[str, str]]) -&gt; str:
    """Escape ``text`` for HTML while resolving/stripping inline "(article N)" citations.

    Claude is instructed (PROMPT_TEMPLATE) to cite articles only inside the
    top_articles/top_stories JSON fields, never inline in prose - but as
    defense in depth (matching the a5c7dcc principle of never trusting
    Claude's raw string for a citation), this scans free-text brief fields
    for citation-like parentheticals before escaping. "(article N[, M ...])"
    is unambiguous and is always resolved to a real link or dropped; a bare
    "(N)" is ambiguous (it may be an ordinary parenthetical number in prose)
    and is only touched when N resolves to a known article id - otherwise
    it's left as plain text. A resolvable id with a URL becomes a real
    inline link whose display text (the source name) is composed by Python,
    never echoed from Claude's string. This is a drop-in replacement for a
    bare ``html.escape(text)`` call on any brief prose field.
    """
    if not text:
        return html.escape(text)

    pieces: List[str] = []
    last_end = 0
    for match in _ARTICLE_CITATION_RE.finditer(text):
        ids_group = match.group("ids")
        if ids_group is not None:
            candidate_ids = _CITATION_ID_RE.findall(ids_group)
        else:
            candidate_ids = [match.group("bare_id")]
            if candidate_ids[0] not in article_index:
                continue  # ambiguous bare "(N)" that isn't a known id - leave untouched

        links = []
        for article_id in candidate_ids:
            entry = article_index.get(article_id)
            if entry and entry.get("url"):
                source = entry.get("source") or "source"
                links.append(
                    f'&lt;a href="{html.escape(entry["url"])}" target="_blank" '
                    f'style="color: #0066cc; text-decoration: underline;"&gt;'
                    f"{html.escape(source)}&lt;/a&gt;"
                )
            elif not entry:
                logger.warning(
                    "Brief prose cited an unresolvable article reference %r; dropping",
                    article_id,
                )

        pieces.append(html.escape(text[last_end:match.start()]))
        pieces.append("(" + ", ".join(links) + ")" if links else "")
        last_end = match.end()

    pieces.append(html.escape(text[last_end:]))
    result = "".join(pieces)
    result = re.sub(r"\s{2,}", " ", result)
    result = re.sub(r"\s+([.,;:!?])", r"\1", result)
    return result.strip()
```

Note: HTML rendering collapses consecutive whitespace visually anyway, so the whitespace cleanup regexes are a hygiene pass on the string itself, not a strict correctness requirement — applying them globally (not just around a stripped match) is safe and simpler.
